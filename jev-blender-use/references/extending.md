# 작업 기능 확장

일반 작업은 [새 agent loop](architecture.md)의 plan·검증·판단 계약으로 확장한다. 아래 정적 snapshot/GLB 관련 항목은 기존 `blender_use.py` 경로에 적용된다.

번들 기능의 범위 밖 요청을 받으면 목표를 좁혀서 이미 제공되는 기능에 맞추지 않는다. 실제 요구와 앱 상태를 확인하고 전용 작업 기능을 구현한다. 예: 애니메이션 루프 검토는 frame별 포즈·접지·루프 연결의 확인이 필요하며 정적 GLB 하나로 완료할 수 없다.

## 확장 경계

- **Codex:** 목표와 완료 조건, 새 알고리즘·API 사용, 원인 분석, 시각 검토, 결과 종합.
- **작업 함수:** 상태 수집, 결정적인 계산, 변환·실행, 결과 확인. 정확한 인자를 받아야 하며 모델 응답 텍스트를 코드로 실행하지 않는다.
- **Jev:** 필요한 맥락이 제공된 제한된 후보 선택·분류·적합성 판단. 이미 정해진 함수·인자를 매번 다시 판단시키지 않는다.

처음 해결한 절차 중 반복될 부분만 입력·출력이 명확한 함수로 추출한다. 사용자 프로젝트 전용 recipe는 그 프로젝트의 적합한 도구 경로에 둔다. 일반화할 근거 없이 설치된 Plugin cache를 수정하거나 공유 skill에 사용자 파일·절대 경로를 넣지 않는다.

## 기능 계약

새 recipe에는 아래 항목 중 실제로 필요한 계약을 둔다.

- 입력 파일·scene·view layer·object ID와 그 상태의 fingerprint
- 지원하는 geometry/rig/material 상태와 명시적으로 미지원인 조건
- 원본 보존 또는 사용자 요청에 따른 변경 범위
- 출력 경로, 재실행 시 충돌 처리, 실패·재개 조건
- 성공을 입증하는 산출물과 필요한 시각·import·runtime 확인

공통 실행기에 추가할 때는 job validator, operation dispatch, 기대 산출물 검사를 함께 갱신한다. 단순 클릭이나 속성 하나마다 새 호출을 만들기보다 의미 있는 작업 단위로 묶는다. Blender data API를 우선 고려하고 operator가 필요하면 scene/view layer/active object/selection/mode와 반환 상태를 확인한다.

GLB exporter의 `use_selection`만으로 scene 범위가 제한되지는 않는다. 단일 scene 출력에는 `use_active_scene`도 명시하고, 원본 scene에 선택된 무관한 오브젝트가 있는 사례에서 결과를 다시 import해 포함 범위를 확인한다. `libraries.write` 결과는 library 파일이므로 사용자에게 일반 `.blend`를 제공할 때는 main-file 저장과 재열기도 확인한다.

캡슐 데모에서 부모 pose bone의 `matrix` 변경 직후 자식의 world-space 목표를 설정하면, 갱신 전 부모 변환으로 계산되어 발 미끄러짐·바닥 침범이 발생했다. 부모 설정 후 dependency graph를 갱신하거나 목표 부모 변환으로 `matrix_basis`를 직접 계산한다. 계획한 궤적과 재열기 후 evaluated 메시의 좌표를 비교해야 이 오류를 검출할 수 있다. Cloth는 bake 이후 저장하고, 새 프로세스에서 캐시 상태와 실제 변형을 확인한다.

## 개선 판단

실제 반복 작업에서 Codex 직접 수행, 스크립트 재사용, 스크립트와 Jev 조합을 구분해 완료 시간·잘못된 자동 처리·개입 횟수·재작업량을 기록한다. Jev 도입 자체를 성공 기준으로 삼지 않는다. 질문 batching은 독립 질문에만 적용하고 앞선 답이 필요한 상태 전이는 코드에서 순차 처리한다.

검증이 요청되거나 현재 작업 지침에서 필요한 경우, 대표 입력·미지원 입력·실패 후 재실행과 실제 산출물을 확인한다. 새 기능의 동작 근거가 확보되면 재사용 대상으로 편입한다. 한 장면에서 성공한 결과를 다른 리그·애드온·버전에 확대하지 않는다.
