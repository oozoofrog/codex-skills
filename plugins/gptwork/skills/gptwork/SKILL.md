# GPT Work

Prepare a self-contained Work request, select GPT-6 Astra and a difficulty-based reasoning effort, verify them, submit once, wait for completion, and bring the full response back into the invoking session for processing. Configuration is part of executing the task, not an optional recommendation. Preserve explicit user settings and constraints. No Desktop gptpro Runner or local runtime is needed.

## Procedure

1. Resolve intent from the request: new Work task, follow-up to a confirmed existing Work task, settings-only change, or local draft/edit. “Review this skill in Work” is a Work request even though the subject is a skill. A bare mention without an objective needs one concise question. A local draft/edit creates nothing.
2. Read [model selection](references/model-selection.md) before any Work submission and [task handoff](references/task-handoff.md) for prompt preparation and delivery. Select GPT-6 Astra by default and choose effort according to question difficulty, state the choice and reason, and reuse the user's authorization instead of asking whether to configure them. Only explicit “keep current settings” or “recommend only” changes this default.
3. Prepare the objective, necessary context, deliverable, constraints, and completion criteria. Default to Korean. Include local content only within the authorized disclosure scope; a path alone is not an attachment. Work does not automatically inherit this conversation, local files, plugins, or Git state. For requested file delivery, read [file attachments](references/file-attachments.md) and verify actual attachment completion in the same composer before Send.
4. Resolve the destination. For a named ChatGPT project, use `list_projects` when available and verify the corresponding project in Work UI. Never substitute a same-named local/Git project. With no project request, use a projectless Work composer. For existing work, confirm identity with `list_threads`/`read_thread` or the matching visible conversation and do not create another task.
5. **Configure before submitting.** Use available supported browser UI to open the intended Work composer, inspect its live model/effort controls, select the chosen supported combination, and read it back. Do not change the current local Codex thread. If values already match, verify and reuse them without toggling. The current `create_thread`/`send_message_to_thread` model overrides are Codex-only: a native Work submission with omitted overrides does not satisfy this gate, even if a browser picker was set elsewhere. Use the same verified Work composer to send the prompt. A future native route is eligible only when its documented Work configuration contract preserves and verifies the settings for that submission.
6. If the model or effort cannot be selected/verified, preserve the completed prompt and report **configuration blocked; not submitted** with the concrete missing capability/action. Do not fall through to a default-model native task, a recommendation-only success, an empty placeholder, or a “wait for settings” message. Continue independent preparation while awaiting login or a required choice.
7. Once the intended destination and both selected values are verified, submit the authorized prompt exactly once through that composer. For settings-only requests, stop after verifying settings without sending a message. For explicit native/default-settings opt-out, follow the constrained native route in the handoff reference.
8. Verify the created task or received follow-up from the actual page/tool result. Report title, observed URL/real ID, model, effort, setting evidence, and delivery state. Treat creation/receipt as an intermediate update, not the final result. On ambiguous submission or timeout, inspect the same task for the submitted request before any retry; never blindly repeat UI Send or native calls. Resolve pending IDs only through supported observations, and never pass `clientThreadId` to tools requiring `threadId`.

9. Read [response return](references/response-return.md). Stay in this invoking session, wait for the submitted Work turn to finish, retrieve its complete final response with supported reads, and evaluate/process it against the original request. Do not finish with only a task link or a promise to return later. A review request returns checked findings; an implementation request continues authorized local edits and validation. Only an explicit create-only/no-wait request skips response waiting.

Use only supported UI APIs and live observations; never bypass a blocked app through scripting, private APIs, cookies, or hidden state. A separately supported browser surface may be used. Configuration failures are incomplete work to report, not permission to silently skip the requirement. Installing/editing this skill does not itself request a live test task, third-party message, publication, or Git change.
