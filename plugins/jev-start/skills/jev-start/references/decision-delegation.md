# 결정 위임 예시

판단의 주제보다 **입력 증거, 기준, 그 답이 바꾸는 행동**으로 위임 범위를 정한다. 아래 예시는 호출 후보이며 모든 작업에서 수행할 체크리스트가 아니다.

## 사용자가 제시한 판단 유형

| 판단 | Jev에 맡길 수 있는 부분 | Codex·코드가 맡는 부분 |
| --- | --- | --- |
| PR merge / request changes? | 현재 diff·리뷰 근거·merge 기준으로 `merge_candidate` / `request_changes` / `needs_evidence` 판단 | 저장소 조사, 현재 HEAD와 필수 CI·리뷰 상태 확인, 명시된 차단 조건 적용, 허용된 실제 merge |
| 이 설계 변경의 위험 수준? | 실패 범위·복구 가능성·호환성 증거를 정의된 위험 수준에 따라 평가 | 영향을 조사하고 숨은 의존성·실패 경로 탐색; 요구하는 증거가 없으면 미확인 유지 |
| A/B/C 중 어느 정책을 선택? | 명시된 목적·제약·우선순위에 맞는 후보 선택 또는 후보별 적합성 평가 | 정책 대안 작성, 필수 조건 필터링, 사용자 우선순위 확보, 수치 가중·선택 결과 적용 |
| 추가 테스트가 필요한가? | 특정 테스트의 assertion·실행 경로가 변경된 요구/오류 경로를 다루는지 판단 | 필수 테스트 규칙 적용, 구현 분석, 테스트 설계·작성·허용된 실행; 실행 여부와 성공은 실제 결과로 확인 |
| 이 결과가 release blocker인가? | 관측한 증상과 영향이 명시된 blocker 정의에 해당하는지 평가 | 릴리스 필수 조건과 검사 결과를 결합; 증거 부족을 non-blocker로 바꾸지 않음 |
| 두 구현 중 요구사항을 더 충족하는 것은? | 요구사항별 근거를 비교해 후보를 고르거나 각 충족도를 평가 | 후보 코드·동작·실행 증거 수집, 성능 측정, 필수 조건과 명시된 우선순위로 종합 |
| confidence가 threshold 이상인가? | 이 수치 비교에는 Jev 호출이 필요 없음 | 응답 스키마·유한 값·범위를 확인하고 코드로 비교 |

`merge_candidate` 같은 명칭은 호출자가 정하는 결과 계약의 예시이며 TypeSafe API의 내장 상태가 아니다. 실제 PR 리뷰나 배포 정책이 정해져 있으면 그 명칭과 동작을 따른다.

## 전달할 최소 결정 맥락

항상 별도 문서나 고정 양식을 만들 필요는 없다. 실제로 결정을 바꾸는 다음 정보만 재사용 가능한 호출에 포함한다.

- 목표와 범위: 현재 해결할 문제, 대상 PR/파일/산출물과 revision·hash 등 최신성 식별자.
- 근거: 관련 diff·요구 원문·관측 결과·반대 증거. 실행한 검사와 실행하지 못한 검사를 구분한다.
- 후보와 기준: 실제 가능한 대안, 필수 제약, 순위·위험 수준의 구체적 정의, 이미 알려진 사용자 우선순위.
- 미확인: 빠진 근거와 결정에 미치는 영향. 필요한 값이 없으면 수집하거나 `needs_evidence`로 반환한다.

예를 들어 테스트가 모두 통과했다는 사실만으로 release blocker가 없다고 묻지 않는다. 변경한 동작, 영향받는 사용자 경로, 테스트의 실제 검증 범위, blocker 정의를 함께 줘야 한다. Codex가 작성한 요약만 평가하는 경우 원문과 실행 결과까지 독립 검토한 것으로 보고하지 않는다.

## 판단을 조합하는 방법

- 하나의 Choice로 끝낼 수 있는 명확한 선택은 그대로 사용한다. 서로 다른 가치 축을 한 질문에 섞어 답이 불투명해질 때만 분리한다.
- 서로 독립적인 요구사항 충족 여부는 Noul로, 정도가 필요한 축은 구체적으로 정의한 Score로 묻는다. 필수 조건의 위반·미확인은 먼저 처리하고, 서로 교환 가능한 선호만 코드에서 가중합한다.
- Score 값은 정의한 수준상의 위치다. 선택의 정확도나 실패 발생 확률로 바꾸지 않는다. Choice/Score confidence는 분포 집중도이며 Noul은 명제의 참일 확률이다.
- 낮은 confidence가 무조건 작업 중단을 뜻하지는 않는다. 동등하게 허용되는 비파괴적 선호라면 명시된 tie-break 규칙을 쓸 수 있다. 누락된 필수 증거·서로 충돌하는 결과·영향이 큰 미검증 선택은 Codex가 원문을 확인한다.
- 위임된 결과를 사용할 조건이 충족되면 정해진 코드 경로에서 소비한다. 모든 답을 Codex가 다시 같은 방식으로 판단하면 위임 비용만 늘 수 있다. 반대로 제2모델을 한 번 호출했다는 사실만으로 독립 검토나 정확도 향상을 보장하지 않는다.
- 같은 답을 얻으려고 반복 호출하지 않는다. 재시도는 서비스 오류 처리나 새 증거·기준으로 질문을 수정한 경우처럼 이유가 있어야 한다. 실제 개선은 전체 지연·비용·잘못된 자동 결정·Codex 개입·재작업으로 판단한다.

## 이 지침이 매 세션 필요한가

`jev-start`는 필수 SDK나 실행 의존성이 아니다. Jev의 기본 성격을 알고 있고 해당 도구에 결정 계약이 있으면 바로 사용할 수 있다. `typesafe-ai`를 사용해 통합 코드를 만드는 작업, 이미 구현된 `jev-blender-use` 호출에 이 스킬을 의무적으로 추가하지 않는다.

특정 작업에서 일반적인 결정 보조까지 쓰고 싶다면 시작할 때 `$jev-start`와 실제 목표를 함께 주는 방식이 간단하다. 같은 작업에서 매 턴 다시 읽거나 호출할 필요는 없다. 독립된 새 세션에서도 같은 적용을 확실히 원하면 관련 지침을 그 세션에 제공해야 하며, 설치된 스킬의 자동 선택을 무조건 보장하지 않는다.

상시 적용을 명시적으로 요청받았을 때만 해당 범위의 프로젝트 지침 또는 사용자 지침에 짧은 조건부 참조를 둔다. 예: “반복되는 의미 판단에 이득이 있을 때 Jev를 선택적으로 활용하고, 위임 기준이 필요하면 jev-start를 읽는다.” 본문 전체를 모든 세션에 복제하거나 매 작업 시작 시 외부 호출을 강제하지 않는다.
