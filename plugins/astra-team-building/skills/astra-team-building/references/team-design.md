# 팀 설계와 조정

팀은 조직도가 아니라 현재 목표를 수행하는 배정이다. 리더는 목표·우선순위·계약·소유권·완료 판정을 맡고 직접 작업도 한다. 같은 사람이 여러 역할을 할 수 있듯 한 세션이 조사·구현·검증·통합을 순차 담당할 수 있다. 필요한 독립 판단만 별도 세션으로 분리한다.

## 일을 나누는 기준

먼저 선행 결과가 필요한 일과 지금 시작할 수 있는 일을 나눈다. 작업 단위마다 산출물, 입력 계약, 허용 경로, 완료 증거를 정한다. 다음 중 실제 이익이 있는 분리만 실행한다.

- 조사 결과 하나가 다음 결정을 앞당기고 리더는 다른 필요한 작업을 진행할 수 있다.
- 계약이 확정된 독립 구현을 별도 환경에서 수행해 전체 완료까지 걸리는 시간을 줄일 수 있다.
- 전문 지식·별도 맥락 또는 독립 검토가 실패 위험을 낮춘다.

공유 인터페이스가 미정이면 그 결정을 먼저 한다. 파일이 다르다는 사실만으로 과제가 독립적이지는 않다. 여러 사람이 같은 조사를 반복하거나 리더가 위임한 구현을 다시 작성하지 않는다.

## 규모 결정

정해진 기본 인원이나 최소 워커 수는 없다. **리더 단독도 정상적인 팀 구성**이다. 가용 슬롯을 채우려 하지 않는다. 동시에 진행할 수 있는 범위는 다음 병목 중 가장 좁은 것으로 제한된다.

- 현재 선행 조건이 충족된 독립 산출물의 수
- 호스트의 가용 슬롯과 사용자의 한도(리더가 슬롯을 차지하는지 포함)
- 격리된 writer 환경과 공유 자원 용량
- 리더가 반환물을 검토·통합할 여력
- 목표 시간·사용량 예산

이 값이 불확실하면 작은 유효 배정으로 시작한다. 다음 독립 과제를 추가했을 때 줄어들 대기와 늘어날 전달·검토·통합 비용을 비교한다. 합리적인 정성 판단으로 충분하며 근거 없는 숫자 점수나 최적 인원 공식을 만들지 않는다.

| 작업 상황 | 가능한 구성과 조정 |
| --- | --- |
| 작고 확정된 수정 | 리더가 구현·검증. 팀 스킬 호출만으로 워커를 만들지 않음 |
| 재현이 필요한 버그 | 리더가 가설·수정을 맡고, 유용한 병렬 수집이 있으면 탐색 역할 추가 |
| 독립 모듈을 연결하는 기능 | 계약 확정 후 필요한 구현 세션을 격리. 결과 도착에 맞춰 검증·통합 |
| 불확실한 설계·데이터 전환 | 리더/전문 역할의 분석을 먼저 수행. 위험에 맞는 독립 검토 후 구현 분리 |
| 하나의 Simulator·기기·GPU에 의존 | 코드/자료 조사는 병렬 가능. 점유가 필요한 검증은 직렬 수행 |

예시는 목표 인원수가 아니다. 세 모델을 골고루 쓰거나 리더·설계자·구현자·테스터·리뷰어·Git 담당을 항상 모두 만드는 방식은 피한다.

## 역할과 수명

- **리더**: 완료 조건, 의존 관계, 배정, 우선순위, 통합 결과를 책임진다. 워커 결과를 기다리는 동안 독립된 유용한 일을 한다.
- **탐색/진단**: 위치·재현·로그·대안의 근거를 반환한다. 결론에 필요한 정보가 없으면 필요한 증거를 지정한다.
- **구현/전문 분석**: 맡은 변경과 그 변경에 필요한 검증을 함께 책임진다. 검증을 전부 다른 역할에 떠넘기지 않는다.
- **검증 담당**: 통합 결과·실제 환경·독립 실패 경로를 확인할 필요가 있을 때 추가한다.
- **독립 리뷰어**: 아래 조건에 따라 원 요구와 실제 산출물의 불일치를 찾는다.
- **통합/Git 담당**: 여러 작업의 병합·충돌·공유 Git 연산이 병목일 때 분리한다. 작은 통합은 리더가 담당하며 Git 연산 자체가 전담 세션 생성 사유는 아니다.

연관된 후속 작업은 기존 세션에 맡긴다. 독립 리뷰, 다른 맥락, 설정 변경이 필요한 경우에만 새 세션을 선택한다. 유휴 세션을 재사용할 때는 모델·effort·작업 경로·실제 상태가 새 과제에 적합한지 확인한다. 재사용 때문에 더 비싼 모델을 무조건 유지하지도, 작은 후속 확인마다 새 세션을 만들지도 않는다.

## 재편 신호

확장은 독립 과제가 준비되고 자원·통합 여력이 있을 때 한다. 축소는 결과 대기, 같은 맥락 설명의 반복, 수정 충돌, 공유 자원 포화, 리뷰 적체가 생겼을 때 한다. 먼저 과제 경계와 의존성을 고치고 필요한 경우 모델·effort를 조정한다. 워커 교체 전 실제 정지와 미커밋 산출물을 확인한다. interrupt가 슬롯 해제를 뜻하는지는 도구 계약을 확인한다.

리더만 전체 팀 확장과 소유권 변경을 조정한다. 워커의 추가 위임 제안은 같은 자원·독립성 기준으로 검토하며 재귀 위임으로 슬롯·예산을 늘리지 않는다.

## 독립 검토

사용자가 요청했거나 여러 구현의 상호작용, 공개 계약, 동시성·상태 전이·데이터 손실 위험에서 독립 관점이 의미 있을 때 별도 리뷰를 배정한다. 단순한 의미 보존 편집이나 근거가 명확한 조회에는 리더 확인이 충분하다. 리뷰어의 모델·effort는 [배정 기준](model-routing.md)을 따른다.

요구사항 원문, 완료 기준, 실제 파일과 고정 snapshot, 필요한 검증 기록을 전달한다. 구현자의 성공 결론이나 예상 정답을 먼저 주지 않는다. 리뷰 중 관련 writer를 멈추거나 불변 snapshot을 제공한다. 리뷰어는 해당 변경을 구현·통합한 세션과 분리하고 제품 파일·Git index/history를 수정하지 않는다.

리뷰어는 PASS / CHANGES_REQUIRED / BLOCKED와 근거 위치·영향·필요한 수정·미확인을 반환한다. 필요한 검증이 없으면 PASS로 추정하지 않는다. 리더는 지적의 타당성을 실제 근거로 판단하고 blocking finding을 해결한다. 수정 뒤 영향을 받은 검증·검토만 다시 수행한다. 자기 검토나 다른 모델을 썼다는 사실을 독립 검토의 증거로 삼지 않는다.
