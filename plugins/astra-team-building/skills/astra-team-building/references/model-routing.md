# 모델과 thinking level 배정

모델은 필요한 판단 범위와 맥락으로, effort는 그 과제에서 필요한 탐색·반례·검증 깊이로 선택한다. 파일 수나 직함만으로 배정하지 않는다. 아래 표는 운영 출발점이며 성능·가격·최적성을 보장하는 측정 결과가 아니다.

## 선택 순서

1. 사용자가 정한 모델·effort·속도·예산·동시성 제한을 **개별 필드와 적용 범위별로** 보존한다. 미지정 필드만 선택한다.
2. 해당 과제의 모호성, 결합도, 실패 영향, 결과를 독립적으로 검증할 수 있는 정도를 본다. 읽기 전용 분석도 어려운 설계 판단일 수 있다.
3. 위임 이익을 확인한 뒤 현재 실행 경로가 지원하는 후보를 고른다. 모델 가용성은 다른 클라이언트의 목록에서 추정하지 않는다.

| 과제/역할 | 출발점 | 깊이가 더 필요한 경우 |
| --- | --- | --- |
| 리더: 목표·계약·배정·통합 판정 | 현재 세션 유지. 새 리더 설정을 요청받으면 Astra `low` 또는 `medium` | 복잡한 설계·상충 요구는 `high`/`xhigh`. 좁고 확정된 목표는 Sol `medium`도 가능 |
| 탐색·자료 추출·재현 수집 | Luna `high` | 의미 해석·여러 원인의 분리가 핵심이면 Sol `medium`/`high` |
| 명세가 분명한 작은 편집·변환 | Luna `high`, 빠르고 직접 검증 가능한 반복 작업은 `low`/`medium`도 후보 | 범위가 늘거나 독립 검증이 어려우면 Sol로 재분류 |
| 기능 구현·버그 수정·회귀 테스트 | Sol `medium` | 얽힌 제어 흐름·가정·경계 사례는 `high`/`xhigh` |
| 아키텍처·동시성·수명·데이터 전환 분석 | Astra `medium`/`high` | 많은 제약과 반례가 남으면 `xhigh`, 결정적 난제에만 `max` 검토 |
| 검증 실행·로그 근거 정리 | Luna `high` 또는 리더 직접 | 테스트 설계·실패 원인 판단은 Sol `high` 또는 Astra 전문 역할 |
| 독립 리뷰 | Sol `high` | 중요한 설계·복합 상태·여러 변경의 상호작용은 Astra `high`/`xhigh`; `max`는 필요성이 설명될 때 |
| 통합·Git 담당 | 단순 조회는 리더 또는 Luna, 정형 통합은 Sol `medium`/`high` | 의미 충돌·복구 판단은 Astra `high`/`xhigh` |

역할의 모델은 고정 신분이 아니다. 동일 세션이 설정을 유지한 채 적합한 여러 책임을 순차 수행할 수 있다. 독립 리뷰어는 자신이 구현하거나 통합한 결과를 독립 검토했다고 하지 않는다. 리더의 실제 모델이 권장값과 달라도 자동 교체하지 않는다.

## thinking level의 사용

공식 출발점은 Astra `low`(화면의 Light), Sol `medium`, Luna `high`다. 다른 모델의 같은 effort를 동일한 비용·지능·시간으로 환산하지 않는다.

| effort | 배정 근거 |
| --- | --- |
| `low` | 명확한 범위와 빠른 피드백; Astra의 일반 출발점 |
| `medium` | 구현·계획·일반 분석에 필요한 균형 |
| `high` | 복잡한 논리 추적·가정 확인·경계 사례; Luna의 출발점 |
| `xhigh` | 여러 제약과 가설을 깊게 비교할 필요 |
| `max` | 비용·대기 증가가 정당화되는 어려운 단일 판단 |
| `ultra` | 지원 경로에서 가장 깊은 reasoning/위임 방식의 의미를 확인한 뒤 선택. 팀을 만드는 필수값이 아님 |

2026-09-26 제작 호스트의 도구 스키마는 Astra·Sol에 `low/medium/high/xhigh/max/ultra`, Luna에 `low/medium/high/xhigh/max`를 표시한다. Luna `ultra`는 지원 대상으로 두지 않는다. 이 표는 영구 카탈로그가 아니므로 실행 때 현재 schema를 확인한다. 화면의 Ultra 설명을 서브에이전트 도구의 effort 필드에 그대로 투영하지 않는다. `none`·`minimal`을 모든 모델에서 쓸 수 있다고 추정하지 않는다.

## 실패·승격·하향 조정

- 입력·인증·환경·기기 부재이면 증거 또는 환경을 먼저 해결한다. effort 상승은 해결책이 아니다.
- 명세가 모호하면 리더가 계약을 좁힌다. 실행 실패만 보고 더 많은 구현자를 투입하지 않는다.
- 과제는 명확하지만 반례·복잡한 논리를 놓치면 동일 모델의 effort 상승 또는 더 적합한 모델을 비교한다. 넓은 맥락·설계 판단이 병목이면 모델 전환을 검토한다.
- 검증 가능한 반복 과제가 안정되면 다음 배정에서 낮은 effort/가벼운 모델을 시도할 수 있다. 사용자 지정값과 완료 기준은 낮추지 않는다.
- 진전 없는 반복은 새 증거 없이 재시도하지 않는다. 원문 오류, 시도한 가설, 현재 diff와 미확인을 회수해 범위·방법·모델 중 필요한 것을 조정한다.

지원되는 모델 변경 기능이 없으면 기존 세션을 중지하고 상태·writer 소유권을 확인한 뒤 새 세션에 인계한다. `followup_task`의 prompt로 모델을 변경했다고 하지 않는다. 명시 조합이 미지원이면 해당 배정만 보류하고 제약을 알린다. 자동 후보가 미지원이면 조건을 충족하는 가용 후보로 바꾼 이유를 설명하되 사용자 제약을 완화하지 않는다.

## 근거

[OpenAI Models](https://learn.chatgpt.com/docs/models)와 [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)를 2026-09-26 확인했다. 공식 모델별 출발점과 더 깊은 reasoning의 tradeoff를 바탕으로 위 역할표를 설계했다. 실제 호출 필드·가용 effort·상속 제약은 [세션 도구](session-tools.md)와 현재 호스트 설명이 권위다. 사용량 절감과 모델별 처리 품질은 별도 실측 대상이다.
