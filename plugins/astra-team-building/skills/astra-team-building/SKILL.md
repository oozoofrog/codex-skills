# Astra Team Building

현재 세션을 리더로 유지하고, 사용자의 목표를 구현·검증·필요한 통합까지 완료할 팀을 구성한다. 최적화 대상은 **완료 품질을 충족하는 전체 시간·사용량·재작업**이다. 인원수, 모델 종류 수, 높은 thinking level 자체를 목표로 삼지 않는다. 사용자 지정 모델·effort·예산·권한과 적용되는 프로젝트 지침이 우선한다.

## 팀 구성과 실행

1. **일과 환경을 파악한다.** 완료 조건, 현재 변경과 작업 경로, 불확실한 계약, 의존 관계, 검증 수단, 실제 사용 가능한 모델·도구·슬롯과 공유 자원을 확인한다. 이미 확인된 정보는 재사용한다. 설계가 필요한 부분과 바로 수행할 수 있는 부분을 구분한다.
2. **필요한 역할만 배정한다.** [팀 설계](references/team-design.md)에 따라 리더가 직접 할 일과 독립 산출물을 나눈다. 역할 하나가 세션 하나를 뜻하지 않는다. 작은 작업이나 순차 의존 작업은 리더 단독으로 완료할 수 있다. 독립 과제가 있고 리더도 유용한 별도 작업을 할 수 있으며 전달·통합 비용보다 이익이 크면 서브에이전트에 위임한다. 사용자 요청 또는 위험에 따른 독립 검토도 위임 근거다.
3. **모델과 thinking level을 따로 고른다.** [모델 배정](references/model-routing.md)의 작업별 출발점에서 시작한다. Astra·Sol·Luna를 모두 사용할 의무는 없다. 이 스킬을 선택하면 적합한 혼합 배정이 기본적으로 가능하며 별도의 `mixed-model` 선언은 필요 없다. 현재 리더의 실행 설정은 스킬로 바뀌지 않는다.
4. **실행 가능한 배정을 알리고 시작한다.** 역할/산출물, 담당 세션과 모델·effort, 변경 경로·환경, 선행 조건, 검증을 짧게 공유한다. 기존 권한으로 진행 가능한 배정은 승인 대기 단계로 만들지 않는다. [세션 도구](references/session-tools.md)와 [전달·상태](references/packets-and-state.md)를 적용해 실제 인자로 설정하고 결과를 회수한다.
5. **병목이 바뀌면 팀을 바꾼다.** 준비된 독립 과제와 리더의 통합 여력이 늘었을 때만 확장한다. 대기·충돌·중복 조사·검토 적체가 생기면 축소하거나 직렬화한다. 같은 맥락의 보완은 기존 세션을 재사용한다. 워커는 재위임이 필요하면 리더에게 제안하며 전체 슬롯·범위 조정은 리더가 맡는다.
6. **증거로 통합하고 종료한다.** 워커의 diff·검증·남은 문제를 완료 조건에 대조한다. 통합된 결과에 필요한 검증을 수행하고 관련 실패를 해결한다. 통과한 검증은 입력 변경·실패·새 근거가 있을 때만 반복한다. 미실행 필수 검증이나 blocking finding이 남으면 전체 완료로 보고하지 않는다.

## 환경과 권한

- 한 worktree에는 한 시점에 한 writer만 둔다. 병렬 구현은 실제 격리된 worktree와 독립 자원이 있을 때 한다. 세션 생성은 파일·Git index·기기·포트·캐시 격리를 만들지 않는다. [작업 환경과 통합](references/workspaces-and-integration.md)을 따른다.
- 리더도 같은 worktree를 쓰면 writer다. 위임한 구현을 중복 수행하지 않는다. read-only 조사도 변하는 파일에 의존하면 snapshot이나 쓰기 중단이 필요하다.
- commit·push·배포·삭제 권한은 원래 요청에서 확인한다. 역할이나 팀 구성은 권한을 추가하지 않는다. 현재 모델·provider·로그인·전역 컨텍스트 설정을 최적화 명목으로 바꾸지 않는다.
- 내부 과제에는 서브에이전트를 쓴다. 사용자가 별도 Codex 작업 생성을 명시한 경우에만 사이드바 작업을 만든다. 위임 도구가 없거나 명시 제약을 충족할 수 없으면 가능한 리더 작업을 계속하고 제한을 밝힌다.

## 검토와 지속적인 개선

여러 구현의 통합, 중요한 공개 계약·상태 전이·데이터 변경 또는 사용자 요청에는 [독립 검토 기준](references/team-design.md#독립-검토)을 적용한다. 검토 범위에 맞는 모델·effort를 고르며 모든 변경에 Astra/max 리뷰어를 붙이지 않는다.

긴 작업은 기존 task state에 팀 배정·소유권·증거와 다음 행동을 기록한다. 별도 전체 상태 문서를 중복 생성하지 않는다. [평가와 조정](references/evaluation.md)은 첫 적용 결과로 배정을 개선하거나 사용자가 비교 실험을 요청할 때 읽는다. 근거 없이 최적 인원·비용 절감률·모델 우열을 확정하지 않는다.

최종 보고는 결과, 변경 경로, 실제 검증과 미확인, 필요한 후속 행동을 중심으로 쓴다. 팀 구성과 조정 이유는 유용한 범위에서 덧붙인다. 요청한 설정, 도구가 수락한 설정, 관측한 실행 설정을 구분하고 설치·로더 노출·실제 행동 검증을 혼동하지 않는다.
