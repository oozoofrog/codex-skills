# 기존 구현·테스트 점검 및 개선

목표는 현재 테스트가 보장하는 유용한 동작을 유지하면서 검출력, 진단력, 실행 안정성 또는 유지비를 개선하는 것이다. 켄트 벡의 Test Desiderata를 상황별 판단 기준으로 쓰고, 모든 속성을 일괄 점수화하지 않는다. 설계 근거가 필요할 때 [연구와 적용 판단](test-improvement-research.md)을 읽는다.

## 1. 현재 보장과 실행 기준 확인

- 요청한 경로의 요구사항·공개 계약, 실제 호출자와 제품 구현, 연결된 테스트·fixture를 함께 읽는다. 코드가 현재 하는 일과 해야 하는 일을 구분한다.
- 기존 테스트 명령과 실행 조건을 확인한다. 입력과 환경이 같은 최신 검증은 재사용하고, 필요한 관련 테스트를 실행해 통과·실패·skip과 중요한 실행 비용을 확인한다. 기존 실패, 환경 문제, 새 변경의 실패를 섞지 않는다.
- 실제 입력이 제품의 어느 경로를 지나 어떤 관측 결과로 검증되는지 연결한다. 대역이 핵심 로직을 대신하거나 저장·이벤트·오류 결과가 검증되지 않는지 살핀다.
- 사용자 영향, 과거 결함, 변경하기 어려운 부분에 근거해 개선 대상을 고른다. 커버리지는 조사할 위치를 찾는 자료이며 숫자를 올리는 것 자체를 완료 목표로 삼지 않는다.

## 2. 문제에 맞는 변경 선택

| 관찰한 문제 | 우선 검토할 개선 | 효과 확인 |
|---|---|---|
| 실행은 되지만 잘못된 결과도 통과함 | 계약에서 도출한 결과·상태·부작용 검증 보강 | 정상 구현은 통과하고 의미 있는 잘못된 동작은 실패하는지 |
| 내부 표현·보조 함수 호출 순서에 지나치게 묶임 | 실제 호출자가 쓰는 경계에서 같은 동작 검증 | 필요한 보호를 유지하며 동작 보존 구조 변경을 허용하는지 |
| 순서·시계·난수·공유 상태에 따라 흔들림 | fixture와 정리 절차 개선, 필요한 외부 의존성 제어 | 의심되는 순서·반복 조건에서 결과가 안정적인지 |
| 긴 시나리오와 중복 검증으로 느리고 진단이 어려움 | 독립적인 변형은 집중된 테스트로, 연결은 필요한 통합 테스트로 구성 | 상호작용 보존, 실패 위치의 명확성, 관련 실행 비용 |
| 중요한 동작의 보호가 없거나 불명확함 | 현재 동작 관찰 또는 요구사항에 근거한 회귀 테스트 | 기대값의 근거와 보호하는 위험이 명확한지 |

테스트 이름·내부 필드·호출 횟수만 보고 기계적으로 판정하지 않는다. 예를 들어 중복 결제·중복 저장 방지가 계약이면 호출 횟수도 의미 있는 검증일 수 있다. 관통 테스트와 집중된 테스트의 역할을 실제 경계에 따라 결정한다.

## 3. 기대값과 실패 해석

- 요구사항·공개 API 계약·독립적으로 계산한 사례가 있으면 그 근거로 기대값을 정한다. 현재 구현에서 복사한 계산식을 테스트의 정답으로 사용하지 않는다.
- 계약이 불명확한 기존 동작은 관찰 결과를 고정하는 테스트로 기록할 수 있다. 이것이 정당한 제품 동작의 증명이라고 주장하거나 이미 알려진 결함을 올바른 동작으로 고정하지 않는다. 판단을 바꾸는 누락된 요구사항만 확인한다.
- 새 보강 테스트가 바로 통과해도 유효할 수 있다. 기존 코드 보호와 테스트 구조 개선을 새 기능의 RED→GREEN 실적으로 포장하지 않는다.
- 실패한 후보는 테스트 오류, 실행 환경 문제, 제품 결함 가능성을 먼저 구분한다. 자동으로 폐기하거나 기대값을 실제 출력에 맞춰 통과시키지 않는다. 제품 수정이 요청 범위에 포함되면 재현 테스트부터 개발 순환으로 전환하고, 그렇지 않으면 결함 근거와 필요한 수정을 보고한다.

## 4. 작은 개선과 채택 검증

- 가장 가치 있는 한 가지 문제부터 기존 스타일과 도구를 사용해 개선한다. 테스트만 개선하는 범위에서는 제품 동작을 유지하고, 필요한 테스트용 구조 정리가 있다면 동작 변경과 구분한다.
- 변경한 테스트를 실행하고 관련 테스트 묶음에서 함께 동작하는지 확인한다. 안정성 문제를 다룰 때 필요한 반복·실행 순서 검사를 선택한다. 무조건 여러 번 전체 검사를 반복하지 않는다.
- 검출력 개선이 불분명하거나 중요한 보호를 대체할 때는 알려진 회귀 또는 한정된 결함 주입으로 확인한다. 가능하면 기존 테스트가 놓치던 결함을 새 테스트가 잡는지 비교한다. 정상 구현의 통과도 함께 확인한다.
- 결함 주입은 격리된 임시 사본에서 수행하고 결과·생성 파일·캐시도 격리한다. 의미가 같은 변경, 빌드 불가, 환경 오류를 결함 검출 성공으로 세지 않는다. 결함 버전이 실제 변경이나 배포본에 남지 않도록 확인한다. 전체 변이 분석이나 새 도구 설치를 기본 의무로 삼지 않는다.
- 기존의 중요한 보장을 잃지 않으면서 구체적인 이득이 있는 변경을 채택한다. 이득은 새 동작 보호·검출력뿐 아니라 안정성·진단력·속도·구조 변경 내성·가독성일 수도 있다. 가독성 같은 정성적 개선은 코드 근거로 설명하고 측정값처럼 표현하지 않는다.
- 중복 테스트 삭제는 위 조건을 만족할 때 선택한다. 개선 이득이 없으면 유지하고, 무관한 실패·불명확한 계약·환경 한계는 분리해 보고한다. 이름이나 줄 수만 다르게 만드는 정리를 이어가지 않는다.

## 결과 설명

점검은 중요한 문제에 대해 **대상 동작 → 현재 테스트의 한계 → 근거 → 제안**을 설명한다. 개선은 여기에 **실제 변경 → 전후 검증 → 남은 한계**를 더한다. 작은 요청에 새 보고 파일이나 고정 점수표를 의무화하지 않는다. 커버리지, 선택한 결함 검출, 전체 회귀, 실제 장치·운영 환경의 증거는 각각의 범위로 보고한다.
