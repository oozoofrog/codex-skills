# Private Electron compatibility boundary

This clean-room runtime was informed by observed behavior in the supplied Pi extension archive; it does not copy its non-`ws` source. The non-`ws` redistribution license was not established. Node 22's built-in WebSocket handles CDP; no dependency is vendored.

Private assumptions are isolated under `runtime/chatgpt-desktop/`:

- exact `app://-/index.html` renderer;
- renderer-to-main `connect-app-host` MessagePort RPC;
- app-host `httpFetch.fetch/cancel`;
- renderer-native WebSocket forwarding through an in-memory `openSocket`/`sendSocket`/`closeSocket` registry;
- Desktop environment and DeviceCheck;
- live model catalog, attestation, conversation POST, `/celsius/ws/user` signing, signed `conversation-*` topic frames, recent-conversation list, and conversation-detail formats.

The response association follows the exact topic returned by the authenticated POST, not an assumed equality between `turn_exchange_id` and WebSocket `turn_id`. The installed Desktop `26.901.31953` likewise validates the handoff shape and passes its topic to the subscription handler; no equality contract for those two IDs was found there. gptpro additionally rejects changes of conversation/turn identity within that topic. This depends on the private service's topic binding; it is not an independently authenticated relationship between the two differently named IDs. See the repository source inventory for the inspected bundle identity.

These are not public OpenAI API contracts. `probe` sends no conversation, `models` uses only the logged-in live catalog, and `ask` accepts one strict UTF-8 message of at most 262,144 bytes. The payload contains no local function signatures and uses normal Chat.

The installed Desktop also retains a topic offset and can reconnect a dropped signed socket. This clean-room runtime currently fails closed on any pre-`done` socket close instead of implementing offset resume. The one POST is still never repeated; explicit `collect-response` is the recovery path. Offset-resume compatibility remains a private-contract risk, not proven response loss in an uninterrupted stream.

On 2026-09-05, approved Schema-6 canary `20260904T163747Z-ask-ffe9bcc6` completed on Desktop `26.901.31953` with exact `gpt-5-6-pro`/`standard`: one dispatch, `completion_source=signed-stream-handoff-v1`, signed assistant evidence, a topic hash, automatic import, and accepted independent evaluation. A tool-role candidate required exact current-branch GET proof, which passed with zero accepted tool routes. No standalone `collect-response` was used. This proves the uninterrupted first-turn path through the runtime's subscription/delta/terminal-done gates; raw frames and per-frame/catchup counts were not retained, and reconnect/resume was not tested.

## Isolated Runner

`launcher-install` creates `~/Applications/gptpro Launcher.app` from deterministic standard-library assets. The launcher contains only an `Info.plist` and a small zsh executable. It starts a second process from the installed, signed `/Applications/ChatGPT.app` with `--user-data-dir=~/Library/Application Support/gptpro/runner/v1/profile`, `--remote-debugging-address=127.0.0.1`, and `--remote-debugging-port=9223`. The ordinary ChatGPT process and profile are not inspected, stopped, or relaunched.

The separate profile is owner-only and may require one attended login if the Desktop app does not reuse the account's system credential state. The runtime never copies credentials from the ordinary profile. `desktop-doctor` requires the exact profile and port arguments on the listening current-user ChatGPT process, then verifies the target, bridge, environment, and DeviceCheck. An unrelated listener on port 9223 is rejected.

This is process/profile isolation, not a redistributed ChatGPT clone. It avoids changing the ordinary app's execution environment without copying proprietary renderer assets or reimplementing authentication. An explicit alternate CDP endpoint is retained only for development diagnosis and is not used by normal consultations.

Install and uninstall use one owner-only nonblocking file lock. A new install uses macOS `RENAME_EXCL`; an update uses `RENAME_SWAP`, verifies the exact pre-swap bundle identity, and moves the prior managed bundle to Trash. A cleanup failure leaves the new launcher installed and returns a recovery path instead of deleting unverified data. Cross-filesystem Trash moves fail before mutation. Process inspection has an explicit unknown state and never opens another ChatGPT instance when inspection fails.

One monotonic deadline covers attestation, POST response headers, and response-stream completion. The current Desktop rejects the archive's `sendMessageFromView` HTTP path and requires app-host `httpFetch`. Matching the installed Desktop RPC client, the result ID is released immediately after decode while its separate Response body pipe remains readable; `httpFetch.cancel` runs after that body completes or is cancelled. A successful POST must return an SSE content type and yield a valid raw `stream_handoff` within the 60-second initial stream boundary; the raw handoff is detected before ordinary compact payload decoding, matching the installed Desktop. The handoff contains `turn_exchange_id` and exactly one `conversation-*` `subscribe_ws_topic`. The runtime obtains a credential-free signed URL from `/celsius/ws/user`, accepts only `wss://ws.chatgpt.com`, and subscribes from offset `0`. It validates the subscription reply, `recovered` state, catchups, conversation/turn identity, parent stream-item chain, decoded SSE deltas, and terminal `done`. Signed `done` is the transport completion signal, but acceptance additionally requires final assistant text, message identity, and `recipient=all`. The signed topic uses the Desktop's 5-second initial-item and 30-second idle boundaries.

Normal `consult` accepts completion only through the signed handoff; missing handoff has no direct-completion fallback. A streamed tool-role node is deferred because compact partials do not yet prove whether it belongs to the accepted branch. Pre-handoff assistant evidence or delta state continued by the signed topic also makes signed-only branch provenance incomplete. After signed `done`, and only then, the runtime may spend at most 30 seconds GET-polling the already known conversation ID and require the deterministic user message plus a zero-tool current branch whose final assistant ID and visible text match the signed result. It never scans the conversation list for this proof, and the completion source remains signed-stream. It persists only the topic hash, completion source, optional content-free branch-proof label, and other bounded evidence, never the raw topic or signed URL. Standalone `collect-response` performs authenticated exact-message conversation GET correlation only as an explicit recovery path after process interruption or signed-stream failure and never sends a prompt. The Python parent closes the one-line authorization input immediately and drains child stderr concurrently so terminal runtime errors cannot be hidden behind an open pipe. Progress exposes only fixed content-free stages, including `current_branch_proof`. On failure after dispatch authorization, child retry metadata is replaced with ambiguous, collect-only/no-resend guidance. Receipts keep the last stage but not prompts, tokens, raw request/conversation IDs, or renderer state. A handoff, ordering, correlation, endpoint, branch-proof, or tool-route violation fails closed instead of selecting another renderer, model, or transport.
